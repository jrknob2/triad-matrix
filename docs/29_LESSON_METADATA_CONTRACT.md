# 29 - Lesson Metadata Contract

**Version:** 1.0
**Status:** Target Contract For Next Implementation Pass
**Last Updated:** July 2026

## Purpose

Provide a stable metadata architecture for Lessons and Exercises that supports:

- Home
- Explore
- Lesson Detail
- Search
- Insights
- Authoring
- Future AI features

The architecture must be extensible without schema changes.

This document owns the meaning of lesson and exercise metadata. It does not own
notation grammar, rendering, navigation, or persistence implementation details.

## Naming Rules

Student-facing labels may be title case:

```text
Timing
Grooves
Rock
Beginner
4/4
```

Stored metadata values should use stable machine-friendly IDs where practical:

```text
timing
grooves
rock
beginner
4/4
```

The UI may render those IDs as human-readable labels. Do not make UI label text
the only stable identity for a metadata value.

# Metadata Categories

There are three classes of metadata.

## 1. Content Metadata

Defined by the lesson author.

Describes the lesson itself.

## 2. System Metadata

Generated by Drumcabulary.

Examples:

- Estimated duration
- Notation complexity
- Exercise count

## 3. User Metadata

Specific to an individual student.

Examples:

- Completion
- Favorite
- Best BPM
- Last Practiced

---

# Content Metadata

Content Metadata is authored and bundled with lesson content. It is independent
of a particular student's progress.

Canonical YAML storage is a `metadata` object on the lesson or exercise. The
exact YAML shape is owned by `docs/20_LESSON_YAML_DATA_ARCHITECTURE.md`, but the
semantic fields are:

```yaml
metadata:
  fundamentals:
    - timing
    - coordination
  musical_vocabulary:
    - grooves
    - fills
  musical_context:
    - rock
  difficulty: beginner
  objectives:
    - consistency
  musical_environment:
    time_signatures:
      - "4/4"
    feels:
      - straight
    subdivisions:
      - eighth_note
  equipment:
    - full_kit
  bpm_recommendation:
    start: 60
    target: 90
```

## Identity

| Field | Multi |
|--------|:-----:|
| Title | No |
| Subtitle | No |
| Summary | No |

Identity may be stored as top-level lesson fields for readability. It is still
Content Metadata semantically.

## Fundamentals

Fundamentals describe **how a drummer develops as a musician**.

These are lifelong abilities.

Multiple values allowed.

Examples:

- Timing
- Technique
- Dynamics
- Coordination
- Independence
- Reading

### Purpose

- Explore
- Insights
- Lesson classification

---

## Musical Vocabulary

Musical Vocabulary describes **what the drummer is learning to play**.

Multiple values allowed.

Examples:

- Grooves
- Fills
- Rudiments
- Linear Playing
- Ostinatos
- Stickings

Future vocabulary may be added without schema changes.

---

## Musical Context

Describes where the musical vocabulary is commonly applied.

Multiple values allowed.

Examples:

- Rock
- Blues
- Jazz
- Funk
- Latin
- Country
- Metal
- Pop
- Fusion

A lesson may belong to multiple musical contexts.

---

## Difficulty

Single value.

Values:

- Beginner
- Intermediate
- Advanced

Difficulty describes the lesson.

It does **not** describe the student.

---

## Objectives

Describes why the lesson exists.

Multiple values allowed.

Examples:

- Speed
- Accuracy
- Endurance
- Consistency
- Musicality
- Creativity
- Coordination
- Independence

Objectives describe teaching intent.

They are stored as metadata but are not intended as primary Explore filters in the MVP.

---

Multiple values allowed.

### Time Signature

### Feel

Examples:

## Equipment

Multiple values allowed.

Examples:

- Practice Pad
- Snare
- Full Kit
- Double Bass
- Hi-Hat Pedal
- Ride Cymbal

---

## BPM Recommendation

Single value.

Example:

- 60–90 BPM

Represents the recommended practice range.

This is instructional guidance.

It is **not** the student's selected BPM.

If the current YAML still stores `tempo.start` / `tempo.target` on exercises,
those values map to the same instructional concept at exercise scope.

# Current Field Migration

Existing lesson YAML contains some fields that predate this contract. During the
next implementation pass, migrate or map them as follows.

| Existing field | Metadata v1 role |
| --- | --- |
| `lesson.title` | Identity title |
| `lesson.overview` | Identity summary until `summary` exists |
| `lesson.objective` | Teaching copy; may inform `objectives` but is not itself a filter list |
| `lesson.level` | Curriculum placement; may seed `difficulty` during migration |
| `lesson.skill` | Legacy curriculum bucket; may seed `musical_vocabulary` during migration |
| `lesson.estimated_minutes` | System Metadata fallback until duration is generated |
| `exercise.why` / `what` / `how` | Teaching copy, not metadata categories |
| `exercise.tempo.start` / `target` | Exercise BPM recommendation |
| notation `subdivision` / `time_signature` / `repeat_count` | Notation-level timing/display metadata; may feed generated Musical Environment |

Do not treat legacy `skill` as the long-term Explore filter model. Explore
should use effective metadata instead.

# Exercise Metadata

Exercises inherit Lesson metadata by default.

Exercises may:

- Add metadata
- Override inherited single-value metadata where appropriate

Example:

### Lesson

```yaml
metadata:
  fundamentals:
    - timing
    - dynamics
  musical_vocabulary:
    - grooves
```

### Exercise

```yaml
metadata:
  musical_vocabulary:
    - fills
  objectives:
    - speed
```

Effective metadata rules:

- Multi-value fields union lesson values and exercise values.
- Single-value fields inherit from the lesson unless the exercise provides a
  value.
- Explicit removal of inherited multi-value metadata is deferred until there is
  a real authoring need.
- Effective metadata is what Explore, Search, Lesson Detail chips, and Insights
  should consume.

# Search

Search should match:

- Titles
- Subtitles
- Summaries
- All Content Metadata
- Notation keywords (future)
- Author keywords (future)

User Metadata should never affect search unless explicitly requested.

Example:

- In Progress

---

# Explore

Explore filters operate entirely on metadata.

## Primary Filters (MVP)

- Fundamentals
- Musical Vocabulary
- Musical Context
- Difficulty
- Time Signature
- Status

## Secondary Filters

- Objectives
- Equipment
- Feel
- Subdivision

Future filters require only adding metadata values.

No UI redesign should be required.

---

# Insights

Insights aggregate primarily by:

- Fundamentals
- Musical Vocabulary
- Objectives

Secondary groupings may include:

- Musical Context
- Difficulty

---

# Authoring Rules

Every Lesson should define:

- Identity
- Fundamentals
- Musical Vocabulary
- Difficulty

Everything else is optional.

Every Exercise inherits Lesson metadata unless overridden.

Avoid duplicate metadata whenever possible.

---

# Extensibility Principles

1. Never encode application behavior into metadata values.
2. New metadata values must not require schema changes.
3. New metadata categories should be additive.
4. User Metadata must never become Content Metadata.
5. Content Metadata should remain independent of UI implementation.
